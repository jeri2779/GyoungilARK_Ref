 # 사용자 지정 AI 코드 규칙

이 문서는 사용자가 직접 정한 코드 작성, 수정, 검토, 보고 규칙이다.
AI 에이전트는 이 규칙을 100퍼센트 준수한다.
규칙이 충돌하면 사용자가 나중에 명시한 더 강한 규칙을 우선한다.


- 5살 아이 시선에서 이해가능하게 설명합니다. 

답변의 모든 줄은 예외 없이 "이모지 + 짧은 라벨 + = + 짧은 설명" 형태로 작성한다. 결론 줄도 예외 없다.
문단 구분은 빈 줄로만 하고, 줄글로 길게 이어 쓰지 않는다.
한줄 리스트 방식으로 끊어서 설명할것

이모티콘 / 기호  매우 적극적으로 활용하여 가독성 무조건 높일것. 절대적임.
 
- 코드는 정보의 보관/계산/출력으로 크게 나누어서 그 역할을 명확히 나눈다. 
- 함수엔 if문으로 조건문을 남발하지 않는다. 실행부는 실행 관련만 작성한다.
- 불필요한 반복문을 작성하지 않는다.
- 불필요한 조건문을 작성하지 않는다.
- 메서드마다 역할 설명 // 문으로 한줄씩 작성한다. (외부인이 봐도 이해 가능하게)


- foreach문은 동적 컬렉션인것들을 제외하면 사용을 금지한다.
- foreach문을 for문으로 우회하지 않는다.
- 데이터의 흐름 구조를 반드시 파악한다.(불필요한 계산 중복 방지)
- 데이터의 계산결과는 반드시 한군데 이상은 받아야 한다.
- 실행부 메서드엔 실행 이외의 조건부 코드를 1개도 작성하지 않는다.
- 데이터의 보관/계산/출력부를 철저히 구분한다.
- CQS 패턴 절대 준수.
- SRP 패턴 준수.
- 한 글자/ 한 단어/매직 넘버 금지

명시적 "진행" 단어 없이 직접 수정 금지

## 2. CQS

- 메서드는 Command와 Query로 명확히 분리한다.
- Query는 상태를 읽고 결과만 반환한다.
- Query는 내부 상태와 외부 상태를 변경하지 않는다.
- Command는 상태 변경만 수행한다.
- Command에서 판단, 검색, 검증, 계산을 수행하지 않는다.
- 한 메서드에서 Command와 Query를 섞지 않는다.
- 실행 전에 모든 계산과 검증을 끝낸다.
- 실행 메서드는 완성된 결과를 받아 그대로 적용한다.
- 객체는 자신이 직접 수행해야 하는 주동 행동만 소유한다.
- 타 객체의 세부 구현과 행동을 대신 결정하지 않는다.

## 3. 실행 메서드 제약

- 실행 메서드는 실행만 담당한다.
- 실행 메서드 안에 `if`를 두지 않는다.
- 실행 메서드 안에 `switch`를 두지 않는다.
- 실행 메서드 안에 null 검사를 두지 않는다.

## 4. 조건문 제약

- `if` 조건에는 이름이 명확한 bool Query 메서드 호출 하나만 둔다.
- if 문 조건에 두가지 이상의 조건이 필요할땐 별도의 bool 메서드로 분리한다. 
- 여러 판단을 하나의 조건문에 합치지 않는다
- Query와 최상위 조립 단계에서 필요한 방어 조건은 메서드 최상단에 둔다.
- 필수 구성 누락은 조용한 `return`이 아니라 즉시 실패로 처리한다.
- 중첩 깊이는 최대 2단계를 넘지 않는다.

## 5. null 제약

- 상위 조립 단계에서 할당이 보장된 객체를 하위 메서드에서 다시 null 검사하지 않는다.
- 불필요한 null 검사를 작성하지 않는다.
- 필수 참조가 없을 때 `return`, `false`, 빈 컬렉션으로 오류를 숨기지 않는다.
- null이면 실행 중에 임시 주입하는 구조를 금지한다.
- 테스트 편의를 위해 정식 코드의 불변 조건을 약화하지 않는다.
- 테스트에는 실제 실행 조건을 재현한 최소 하네스를 구성한다.

## 6. 물음표 문자 금지

- 작성하거나 수정하는 코드에 `?` 문자를 사용하지 않는다.
- 삼항 연산자를 사용하지 않는다.
- 이벤트 호출도 물음표 문자를 사용하지 않는 구조로 작성한다.

## 7. 반복과 탐색

- `foreach`를 작성하지 않는다.
- `foreach`를 `for`나 `while`로 단순 치환한 것을 해결책으로 제안하지 않는다.
- `Find` 메서드를 작성하거나 제안하지 않는다.
- 과거의 `Find` 접두사 정의보다 최신 `Find` 절대 금지 규칙을 우선한다.
- 타입, 이름, 태그를 이용한 런타임 탐색을 금지한다.
- 단일 대상을 얻기 위한 컬렉션 전체 탐색을 금지한다.
- 탐색을 다른 이름으로 위장하지 않는다.
- 고정 관계를 반복문으로 대체하지 않는다.
- 이미 알고 있는 대상은 직접 참조한다.
- 키가 있는 대상은 단건 접근한다.
- 생성한 객체는 생성 결과 참조를 즉시 저장한다.

## 8. 인터페이스 절대 금지(현재 프로젝트 한정)

- 인터페이스를 새 설계로 제안하지 않는다.
- 단 Map폴더내에서만의 사용이라면 예외적으로 허용한다.

## 9. 클래스와 책임

- 1클래스는 정확히 1역할만 담당한다.
- 계산, 검증, 실행, 탐색, 상태 저장, 이벤트 구독을 한 클래스에 섞지 않는다.
- 클래스명과 스크립트명만 보고 기획자가 역할을 즉시 이해할 수 있어야 한다.
- 역할이 둘 이상으로 읽히는 이름을 금지한다.
- 동사와 명사로 이중 해석되는 이름을 금지한다.
- SRP를 반드시 지킨다.

## 10. 메서드 이름

- 메서드명은 PascalCase를 사용한다.
- 메서드명은 동사와 목적어 순서로 작성한다.
- 기본적으로 2단어를 사용한다.
- 최대 3단어에서 4단어 안에서 역할을 명확히 표현한다.
- 클래스명과 매개변수 타입에 이미 드러난 문맥을 메서드명에서 중복하지 않는다.
- 추상적인 표현과 목적어 생략을 금지한다.
- 이중으로 해석될 수 있는 단어를 사용하지 않는다.
- `Check`처럼 판단 대상과 기준을 숨기는 이름을 사용하지 않는다.
- `GetCover`처럼 가져오기와 덮기 동작으로 이중 해석되는 이름을 사용하지 않는다.
- `Get`은 O(1)의 즉시 단건 접근이며 순수 Query일 때만 사용한다.
- `Get` 내부에서 검색, 계산, 상태 변경을 하지 않는다.
- `Find`는 사용하지 않는다.
- `Set`은 외부 값을 받아 내부 상태만 변경하고 반환값을 갖지 않는다.
- `Is`, `Can`, `Has`는 상태를 바꾸지 않는 bool Query에만 사용한다.
- `Try`는 예상 가능한 도메인 실패를 bool 결과로 표현할 때만 사용한다.
- `Try`는 필요할 때 out 매개변수를 사용할 수 있다.
- 필수 구성 누락에 `Try`를 사용하지 않는다.
- `Try` 결과를 무시하지 않는다.
- `On`은 이벤트나 콜백에 대한 수동적 반응에만 사용한다.
- 주동 행동은 원형 동사를 사용한다.
- 피동 반응은 `On` 또는 의미가 명확한 과거분사 형태를 사용한다.
- 실행 비용과 부작용을 이름에서 숨기지 않는다.

## 11. 매개변수 이름

- 매개변수명은 camelCase를 사용한다.
- 매개변수명은 2글자 이상의 완전한 단어 조합으로 작성한다.
- `d`, `h`, `p`, `go`, `pt` 같은 수학식 축약과 단축어를 사용하지 않는다.
- GameObject 매개변수도 역할이 드러나는 완전한 이름을 사용한다.
- `for` 루프 인덱스의 `i`, `j`, `k`만 단일 문자를 허용한다.
- 람다 식별자는 문맥이 명확할 때 단일 문자를 허용한다.
- 순수 기하학과 수학 연산의 `x`, `y`, `z`만 단일 문자를 허용한다.

## 12. 매직 넘버

- 의미가 있는 숫자와 문자열 리터럴을 코드에 직접 입력하지 않는다.
- 반복 경계처럼 언어 구조상 명확한 값과 순수 수학 상수를 제외하고 이름을 부여한다.
- 반복 사용되는 값은 `const`, `readonly`, `enum` 중 책임에 맞는 형태로 선언한다.
- 값의 의미와 단위를 이름에서 알 수 있어야 한다.

## 13. 계산 결과

- 계산 담당은 소비자가 바로 사용할 수 있는 최종 결과를 만든다.
- 중간 좌표 목록과 생자료만 반환하고 소비자에게 해석을 떠넘기지 않는다.
- 계산 결과에는 이후 검증, 실행, 제거에 필요한 확정 정보를 포함한다.
- 실행 담당은 계산 결과를 다시 순회하거나 재계산하지 않는다.
- 같은 결과를 검증, 실행, 제거 단계마다 다시 계산하지 않는다.
- 복수 상태가 필요하면 계산 단계에서 최종 결과를 만들고 저장한다.
- 소비자는 계산 결과의 완성된 값만 Get한다.


## 15. 실패 정책

- 필수 데이터가 없으면 즉시 실패한다.
- null을 반환해 잘못된 상태를 호출자에게 떠넘기지 않는다.
- 빈 결과를 반환해 오류를 숨기지 않는다.

## 16. 문서 주석과 이름

- XML `summary` 태그를 사용하지 않는다
- 주석은 한줄로 하는 역할만 간결히 요약 작성한다. 

## 17. 설계 제안 보고

- 구현 방법을 제안할 때는 서로 구분되는 실행 가능한 방법을 최소 3가지 제시한다.
- 각 방법에 제안 이유와 핵심 구조를 적는다.
- 각 방법에 변경 범위를 적는다.
- 각 방법에 장점, 단점, 실패 위험을 적는다.
- 각 방법에 검증 항목을 적는다.
- 각 방법에 단기 일정과 1년 유지보수 영향을 적는다.
- 각 방법에 되돌리기 가능성과 비용을 적는다.
- 마지막에 추천 순위, 추천 이유, 채택 기준을 명시한다.

## 18. AI 답변 형식

- 코드를 제시하거나 수정안을 작성할 때 컨벤션 준수 여부를 간단히 표시한다.
- 사용자가 전체 코드를 요구하지 않으면 전체 파일을 다시 출력하지 않는다.
- 변경된 범위의 Diff 또는 Partial Code 위주로 제공한다.
- 수정하지 않은 파일과 관련 없는 코드를 답변에 섞지 않는다.
- 직접 수정한 경우 검증 결과와 남은 위험을 함께 보고한다.
- 가독성은 1원칙이다. 절대 예외는 없다.
- 이모티콘/ 시각화 자료를 매우 적극적으로 활용할것. 

## 19. 검증

- 수정한 코드의 실제 호출부를 확인한다.
- 사용되지 않는 실험 코드를 정식 구현으로 판정하지 않는다.
- 빈 직렬화 슬롯과 과거 직렬화 잔여 데이터를 구분한다.
- 중복 등록, 중복 구독, 중복 해제를 검증한다.
- 텍스트 파일은 UTF-8 인코딩을 유지한다.
